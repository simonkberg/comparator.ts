# RFC 0001: comparator.ts v2

Status: draft, for review.

This document specifies the v2 API of `comparator.ts` and the plan to implement it. It follows
from the review of the v1 implementation and is meant to be the single reference for the release:
the public surface, the ordering guarantees every built-in makes, a reference implementation, a
migration guide, and the sequence of pull requests.

Every signature in this document was type-checked under the repository's `tsconfig.json`
(`@tsconfig/strictest`), and every behavior was run against a prototype of the reference
implementation on Node.js 24. Benchmarks quoted below come from that prototype.

## 1. Decisions to confirm

These are the calls made while writing this document. Each can be reversed without affecting the
rest of the design. Silence means agreement.

1. **Nullish handling is one case, named `nullish`.** The methods are `.nullishFirst()` and
   `.nullishLast()`. `null` and `undefined` are treated identically. There are no `null`-only or
   `undefined`-only helpers, and the v1 free functions `nullsFirst` and `nullsLast` are removed.
   Reasoning: `Array.prototype.sort` never passes bare `undefined` to a comparator at all (it always
   moves it to the end), so the distinction can only ever matter inside keys; there it is rare enough
   that a three-line custom comparator, shown in the README, is a better answer than four extra
   exports. `nullish` is the language's own term (`??`, `?.`) and matches the `T | null | undefined`
   in the signature exactly, where `nulls` (SQL, Java) would be a lie in TypeScript.
2. **`stringComparator` becomes code-unit order.** Locale-aware ordering moves to a new
   `localeComparator(locales?, options?)` factory backed by `Intl.Collator`. Reasoning: deterministic
   across runtimes, same speed as the V8 fast path for `localeCompare`, and matches every other
   sorting library's default. Locale-aware sorting is an explicit choice that names its locale.
3. **Key-based chaining is a separate method, `thenBy`, not an overload of `thenComparing`.**
   A one-argument key mapper and a two-argument compare function cannot be told apart reliably at
   runtime (`fn.length` lies for rest and default parameters) nor at the type level (a one-parameter
   function is assignable to a two-parameter function type). Two methods with distinct names are
   simpler to explain than overload rules. Alternative name if you prefer symmetry:
   `thenComparingBy`.
4. **`Comparator<T>` becomes invariant in `T`.** In v1 a `Comparator<Person>` could be assigned to a
   `Comparator<Employee>` variable. Any method that accepts a plain compare function or a key mapper
   makes that impossible, because TypeScript compares callback parameters covariantly. The
   workaround is `comparator<Employee>(personComparator)`, which returns the same object and only
   changes the type. Every other v1 use (passing to `sort`, `toSorted`, `thenComparing`,
   `comparing`) is unaffected.
5. **`naturalOrder` is a plain compare function, not a `Comparator`.** It is overloaded per kind
   and cannot carry `.reversed()` without a second interface. `comparator<number>(naturalOrder)`
   or any built-in gives the method-bearing form.
6. **Mixed kinds under natural order are a type error and unspecified at runtime.** No per-call
   `typeof` check is made. The type constraint on `comparing` and `thenBy` rejects unions of
   different kinds.
7. **No chain flattening.** Storing a chain as a flat array and looping over it measured 7% faster
   than nested closures on three-key sorts. Not worth the extra representation.
8. **Keep the CommonJS build.** Dropping it has no user-facing benefit for v2 and tsdown makes it
   free. Can be revisited in v3.
9. **Add `fast-check` as a dev dependency** for the comparator-law tests in section 7. A hand-rolled
   generator would work, but `fast-check` shrinks counterexamples, which is what makes these tests
   worth having.
10. **Add `bigintComparator`.** One line, and it keeps the per-kind set symmetric with
    `Comparable`.

## 2. Goals and non-goals

Goals:

- Every built-in comparator is a total order on its domain. Sorting any array of its domain type
  gives the same result on every runtime and regardless of input order.
- One way to do each thing. Combinators are methods on the comparator; construction is a free
  function.
- Zero overhead beyond one closure per derived comparator. No allocation per comparison.
- The README states the full ordering contract in one screen.

Non-goals:

- Property-name keys (`comparing("age")`). They do not help inference and add a second spelling.
- A cross-kind natural order (numbers before strings, and so on).
- Comparators for objects, arrays, or tuples. `comparing` plus `thenBy` covers structured keys.

## 3. Public API

```ts
/** A function that compares two values of type T. Negative: a before b. Zero: tie. Positive: a after b. */
export type CompareFn<T> = (a: T, b: T) => number;

/** The kinds that naturalOrder can compare. */
export type Comparable = number | bigint | string | boolean | Date;

/** The natural order for each kind. Overloaded so that both arguments must be the same kind. */
export interface NaturalOrder {
  (a: number | bigint, b: number | bigint): number;
  (a: string, b: string): number;
  (a: boolean, b: boolean): number;
  (a: Date, b: Date): number;
}

export interface Comparator<T> extends CompareFn<T> {
  /** The opposite order. Cached, and reversed().reversed() is this comparator. */
  reversed(): Comparator<T>;

  /** This order, then compareFn to break ties. Accepts any compare function. */
  thenComparing(compareFn: CompareFn<T>): Comparator<T>;

  /** This order, then the natural order of mapper(value) to break ties. */
  thenBy<U extends Comparable>(mapper: (value: T) => U): Comparator<T>;
  /** This order, then compareFn applied to mapper(value) to break ties. */
  thenBy<U>(mapper: (value: T) => U, compareFn: CompareFn<U>): Comparator<T>;

  /** This order over non-nullish values, with null and undefined before everything else. */
  nullishFirst(): Comparator<T | null | undefined>;
  /** This order over non-nullish values, with null and undefined after everything else. */
  nullishLast(): Comparator<T | null | undefined>;
}

/** Wraps a compare function. Returns the argument itself if it is already a Comparator. */
export const comparator: <T>(compareFn: CompareFn<T>) => Comparator<T>;

/** Compares values by the natural order of mapper(value). */
export function comparing<T, U extends Comparable>(mapper: (value: T) => U): Comparator<T>;
/** Compares values by compareFn applied to mapper(value). */
export function comparing<T, U>(mapper: (value: T) => U, compareFn: CompareFn<U>): Comparator<T>;

/** The natural order. See section 4 for the exact rules. */
export const naturalOrder: NaturalOrder;

export const numberComparator: Comparator<number>;
export const bigintComparator: Comparator<bigint>;
export const stringComparator: Comparator<string>; // code-unit order
export const booleanComparator: Comparator<boolean>; // false before true
export const dateComparator: Comparator<Date>; // by time value

/** Locale-aware string order backed by Intl.Collator. Same arguments as the Collator constructor. */
export const localeComparator: (
  locales?: Intl.LocalesArgument,
  options?: Intl.CollatorOptions,
) => Comparator<string>;
```

Removed from v1: `nullsFirst`, `nullsLast`. Changed: `thenComparing` parameter type
(`Comparator<T>` to `CompareFn<T>`), `stringComparator` ordering, `numberComparator` and
`dateComparator` behavior on `NaN` and invalid dates.

### Usage

```ts
type Feature = { enabled?: boolean; name: string; createdAt: Date; priority: number };

const byPriority = comparing((f: Feature) => f.priority); // natural order, no comparator needed
const byName = comparing((f: Feature) => f.name, localeComparator("en"));
const byEnabled = comparing((f: Feature) => f.enabled, booleanComparator.reversed().nullishLast());

features.toSorted(byEnabled.thenBy((f) => f.priority).thenBy((f) => f.name));
features.toSorted(byPriority.reversed().thenComparing(byName));
features.toSorted(byPriority.thenComparing((a, b) => a.name.length - b.name.length));

[3, 1, 2].toSorted(naturalOrder); // [1, 2, 3], and never the lexicographic default
```

## 4. Ordering contract

This section is normative and is reproduced in the README.

**Total order.** Every built-in comparator and everything derived from one through the methods above
is a total order on its declared domain: reflexive, antisymmetric, transitive, and consistent. Sorting
any array of the domain type is deterministic across runtimes and input orders. User-supplied compare
functions passed to `comparator`, `comparing`, `thenComparing`, and `thenBy` must themselves be
consistent; the library cannot repair an inconsistent one.

**Natural order** (`naturalOrder`, and the default for `comparing` and `thenBy`):

| Kind              | Rule                                                                                                |
| ----------------- | --------------------------------------------------------------------------------------------------- |
| number, bigint    | Numeric. `-0` equals `0`. `NaN` equals `NaN` and sorts after everything else, including `Infinity`. |
| number vs. bigint | Numeric and exact; `2n` equals `2`. Allowed because `<` handles it exactly.                         |
| string            | UTF-16 code-unit order (the order of `<` on strings). Uppercase before lowercase.                   |
| boolean           | `false` before `true`.                                                                              |
| Date              | By time value. Invalid dates equal each other and sort after every valid date.                      |
| mixed kinds       | Rejected by the type checker. Unspecified at runtime.                                               |

**Built-ins.** `numberComparator`, `bigintComparator`, `stringComparator`, `booleanComparator`, and
`dateComparator` are `naturalOrder` narrowed to one kind. `localeComparator(locales, options)` is
`new Intl.Collator(locales, options).compare`; its order depends on the locale and on the runtime's
ICU data, which is the point of opting into it.

**Ties.** A result of `0`, `-0`, or `NaN` from the first comparator counts as a tie and hands off to
the next one in `thenComparing` and `thenBy`. This is the same rule `Array.prototype.sort` applies to
`NaN`.

**Nullish.** `nullishFirst` and `nullishLast` treat `null` and `undefined` as one value, equal to each
other, and never pass either to the wrapped comparator. Two caveats that come from JavaScript, not
from this library: `Array.prototype.sort` and `toSorted` never pass bare `undefined` elements to any
comparator and always place them last, so `nullishFirst` moves `undefined` only when it appears
inside a key (`comparing((o) => o.maybe, cmp.nullishFirst())`); and `reversed()` on a nullish
comparator reverses the nullish placement too, so `cmp.nullishLast().reversed()` puts nullish values
first.

**Identity.** `reversed()` is cached per comparator, and `c.reversed().reversed() === c`.
`thenComparing`, `thenBy`, `nullishFirst`, and `nullishLast` return a new comparator on every call.
`comparator(c)` returns `c` itself when `c` was produced by this library, so retyping is free. The
library never mutates a function it did not create.

## 5. Type-level behavior

- **Inference of `T` in `comparing` needs an annotation.** TypeScript cannot infer the element type
  from a later `sort` call, so write `comparing((p: Person) => p.age)` or annotate the result as
  `Comparator<Person>`. `thenBy` infers its mapper's parameter from the receiver, so only the first
  link in a chain needs the annotation. The README shows this idiom once, up front.
- **Nullable keys need an explicit comparator.** `comparing((p: Person) => p.nick)` with
  `nick?: string` is an error because `string | undefined` is not `Comparable`; the fix
  `comparing((p: Person) => p.nick, stringComparator.nullishLast())` is what the error should point
  the reader to.
- **`comparator(naturalOrder)` without a type argument resolves to `Comparator<Date>`** (the last
  overload wins). Always pass the type argument: `comparator<bigint>(naturalOrder)`. The built-ins
  do so.
- **Invariance.** See decision 4. `employees.sort(personComparator)` and
  `employeeComparator.thenComparing(personComparator)` keep working, because those positions take a
  compare function, not a `Comparator`. Only a variable or parameter annotated `Comparator<Employee>`
  rejects a `Comparator<Person>`; library authors should accept `CompareFn<T>` in their own
  signatures and return `Comparator<T>`.

These rules are pinned by the type tests in section 7.

## 6. Reference implementation

This is the complete `index.ts` minus documentation comments. It is the prototype that was
type-checked and benchmarked; the implementation PRs should reproduce it, not redesign it.

```ts
export type CompareFn<T> = (a: T, b: T) => number;
export type Comparable = number | bigint | string | boolean | Date;

export interface NaturalOrder {
  (a: number | bigint, b: number | bigint): number;
  (a: string, b: string): number;
  (a: boolean, b: boolean): number;
  (a: Date, b: Date): number;
}

export interface Comparator<T> extends CompareFn<T> {
  reversed(): Comparator<T>;
  thenComparing(compareFn: CompareFn<T>): Comparator<T>;
  thenBy<U extends Comparable>(mapper: (value: T) => U): Comparator<T>;
  thenBy<U>(mapper: (value: T) => U, compareFn: CompareFn<U>): Comparator<T>;
  nullishFirst(): Comparator<T | null | undefined>;
  nullishLast(): Comparator<T | null | undefined>;
}

export const naturalOrder: NaturalOrder = (a: Comparable, b: Comparable): number => {
  if (a < b) return -1;
  if (a > b) return 1;
  if (a === b) return 0;
  // Neither ordered nor identical: equal Dates, NaN, or invalid Dates.
  const x = Number(a);
  const y = Number(b);
  if (x === y) return 0;
  const xNaN = x !== x;
  const yNaN = y !== y;
  return xNaN ? (yNaN ? 0 : 1) : -1;
};

const comparators = new WeakSet<CompareFn<never>>();

export const comparator = <T>(compareFn: CompareFn<T>): Comparator<T> =>
  comparators.has(compareFn) ? (compareFn as Comparator<T>) : create<T>((a, b) => compareFn(a, b));

// `fn` must be a closure this module created, never a user-supplied function, because it is mutated.
const create = <T>(fn: CompareFn<T>, reverse?: Comparator<T>): Comparator<T> => {
  const self = fn as Comparator<T>;
  let reversed = reverse;
  self.reversed = () => (reversed ??= create<T>((a, b) => fn(b, a), self));
  self.thenComparing = (other) => create<T>((a, b) => fn(a, b) || other(a, b));
  self.thenBy = <U>(mapper: (value: T) => U, other: CompareFn<U> = naturalOrder as CompareFn<U>) =>
    create<T>((a, b) => fn(a, b) || other(mapper(a), mapper(b)));
  self.nullishFirst = () => nullish(fn, -1);
  self.nullishLast = () => nullish(fn, 1);
  comparators.add(self);
  return self;
};

const nullish = <T>(fn: CompareFn<T>, nullishSign: -1 | 1): Comparator<T | null | undefined> =>
  create<T | null | undefined>((a, b) => {
    if (a == null) return b == null ? 0 : nullishSign;
    if (b == null) return -nullishSign;
    return fn(a, b);
  });

export function comparing<T, U extends Comparable>(mapper: (value: T) => U): Comparator<T>;
export function comparing<T, U>(mapper: (value: T) => U, compareFn: CompareFn<U>): Comparator<T>;
export function comparing<T, U>(
  mapper: (value: T) => U,
  compareFn: CompareFn<U> = naturalOrder as CompareFn<U>,
): Comparator<T> {
  return create<T>((a, b) => compareFn(mapper(a), mapper(b)));
}

export const numberComparator = comparator<number>(naturalOrder);
export const bigintComparator = comparator<bigint>(naturalOrder);
export const stringComparator = comparator<string>(naturalOrder);
export const booleanComparator = comparator<boolean>(naturalOrder);
export const dateComparator = comparator<Date>(naturalOrder);

export const localeComparator = (
  locales?: Intl.LocalesArgument,
  options?: Intl.CollatorOptions,
): Comparator<string> => comparator(new Intl.Collator(locales, options).compare);
```

Notes on the implementation:

- `naturalOrder` takes the fast path (`<`, `>`, `===`) for every primitive comparison. The `Number()`
  branch is reached only for equal or invalid `Date` pairs and for `NaN`.
- `comparator` wraps a user function once so that the user's function is never mutated. Every
  derived comparator is a closure this module owns, so `create` attaches the methods to the closure
  directly instead of wrapping again. This removes one call frame per comparison from every derived
  comparator and measured 11% faster on three-key chains than v1's double wrapping.
- The `||` in the chain implements the tie rule from section 4 (`0`, `-0`, and `NaN` are all
  falsy).
- The `WeakSet` brand is what makes `comparator` idempotent and `reversed()` linkable. Duck typing
  on `.reversed` would also work but would misclassify unrelated objects.

### Measured cost

Node.js 24, 300,000 elements, median of 7 sorts, prototype vs. the published v1 bundle.

| Sort                                   | v1 (ms) | v2 (ms) |
| -------------------------------------- | ------- | ------- |
| numbers, built-in comparator           | 178     | 135     |
| numbers, hand-written `<`/`>`          | 98      | 98      |
| strings, built-in comparator           | 196     | 188     |
| strings, `localeComparator()`          | n/a     | 334     |
| objects, three-key chain               | 336     | 299     |
| objects, three-key chain, hand-written | 128     | 128     |

The NaN-safe number comparator is faster than v1's subtraction, not slower. `Intl.Collator` is
about 1.75x slower than code-unit order in V8, which is a cost of locale awareness and not something
to hide with a fast path; the README should state it.

## 7. Tests

All tests stay in `index.test.ts` under `node:test`, plus one new type-test file.

**Unit tests** (replace the v1 suite; keep its structure):

- `naturalOrder`: every row of the table in section 4, including `-0`/`0`, `NaN` pairs, `Infinity`
  pairs, `number` vs. `bigint`, invalid `Date` pairs, and a sort of `[3, NaN, 1, 2]` from both
  input orders.
- `stringComparator`: `["b", "A", "a", "B"]` sorts to `["A", "B", "a", "b"]`.
- `localeComparator`: same input sorts to `["a", "A", "b", "B"]` under `"en"`; `{ numeric: true }`
  orders `"a9"` before `"a10"`.
- `comparator`: wraps a function; returns its argument when given a comparator; does not mutate the
  argument (no `.reversed` property appears on the user's function).
- `reversed`: reverses; cached; `reversed().reversed()` is the original; reverses a nullish
  comparator's nullish placement.
- `thenComparing`: accepts a plain function and a comparator; a `NaN` or `-0` first result hands
  off to the second comparator; three-link chain.
- `thenBy`: natural default; explicit comparator; chain of three keys; mapper parameter inferred
  from the receiver.
- `nullishFirst` / `nullishLast`: `null` placement in a bare array; `undefined` placement through a
  key; both nullish values equal; bare `undefined` in an array is placed last by `sort` regardless
  (documented quirk, tested so it is never "fixed" by accident).
- The README example, unchanged in spirit, as an end-to-end test.

**Law tests** (`fast-check`, in the same file): for each built-in and for
`comparing(...).thenBy(...).nullishLast()` and `.reversed()` over generated arrays including `NaN`,
invalid dates, `null`, and `undefined`: antisymmetry (`sign(c(a, b)) === -sign(c(b, a))`),
transitivity, and consistency of `sort` output across shuffles of the same input.

**Type tests** (`index.types.test.ts`, type-checked by the existing `tsc --noEmit` step, never
executed): one `// @ts-expect-error` per rule in section 5 and one positive case per signature in
section 3, including `comparator<Employee>(personComparator)` compiling and the contextual-typing
form `const c: Comparator<Person> = comparing((p) => p.age)`.

## 8. Migration guide (v1 to v2)

| v1                                        | v2                                                                               |
| ----------------------------------------- | -------------------------------------------------------------------------------- |
| `nullsLast(cmp)`                          | `cmp.nullishLast()` (wrap a plain function first: `comparator(fn)`)              |
| `nullsFirst(cmp)`                         | `cmp.nullishFirst()`                                                             |
| `comparing(key, cmp)`                     | Unchanged. `cmp` is now optional for `Comparable` keys.                          |
| `a.thenComparing(comparing(key, cmp))`    | `a.thenBy(key, cmp)` or `a.thenBy(key)` for natural order                        |
| `a.thenComparing(cmp)`                    | Unchanged, and now also accepts a plain `(a, b) => number`.                      |
| `stringComparator` (locale-dependent)     | `localeComparator()` for the old behavior; `stringComparator` is code-unit order |
| `numberComparator` with `NaN` in the data | Now deterministic: `NaN` last. Previously the sort output was undefined.         |
| `const c: Comparator<Sub> = superCmp`     | `const c = comparator<Sub>(superCmp)`                                            |
| `comparator(fn).reversed().reversed()`    | Now returns the original comparator instead of a new wrapper.                    |

## 9. Implementation plan

Three pull requests, landed in order on `main`. Each carries its own tests, regenerated `docs/`
(the porcelain check requires it), and a changeset. The existing `drop-node-20` changeset already
marks the next release as major, so the version lands as 2.0.0 whenever the release PR that
changesets opens is merged; nothing is published between these PRs.

### PR 1: core representation and combinators

- Replace `index.ts` with section 6 minus `localeComparator` and the primitive changes (keep v1's
  primitive bodies for this PR so the diff is about structure).
- Add `Comparable`, `NaturalOrder`, `naturalOrder`, `bigintComparator`.
- `comparing` overloads with the natural default; `thenComparing(CompareFn)`; `thenBy`;
  `nullishFirst` / `nullishLast`; idempotent `comparator`; involutive `reversed`.
- Remove `nullsFirst` / `nullsLast` and their docs.
- Update `oxlint.config.ts`: the `eqeqeq` exemption comment names `NullComparator`; point it at
  `nullish`. Check whether `unicorn/prefer-native-coercion-functions` or similar fires on the
  `Number()` calls and disable narrowly if so.
- Tests: unit tests for everything above; the type-test file.
- Changeset (major): lists the removals and renames from section 8.

### PR 2: primitive semantics

- `numberComparator`, `dateComparator`, `booleanComparator`, `stringComparator` become
  `comparator<K>(naturalOrder)`.
- Add `localeComparator`.
- Tests: the `naturalOrder` table, string ordering, locale ordering.
- Changeset (major): `stringComparator` ordering change, `NaN` and invalid `Date` handling,
  `localeComparator` added.

### PR 3: guarantees and packaging

- `fast-check` dev dependency and the law tests.
- `"sideEffects": false` in `package.json`.
- README rewrite: installation, the inference idiom, the usage block from section 3, the ordering
  contract from section 4 verbatim, the invariance note, the migration table.
- Regenerate `docs/`.
- Changeset (patch, folded into the same release): tree-shaking hint.

### Release

1. Merge the three PRs.
2. Merge the "Version Packages" PR that the release workflow opens; it bumps to 2.0.0 and publishes.
3. Tag nothing by hand; the workflow does it.
